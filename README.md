# Styrklog

An offline iOS app that turns a [StrengthLog](https://www.strengthlog.com/) CSV export into
a front/back muscle heat map, so you can see which muscle groups your training is
actually neglecting.

No auth, no backend, no persistence — import a CSV, read the map, close the app.

## Running it

```bash
npm start
```

Then press `i` for the iOS Simulator, or scan the QR code with Expo Go on your phone.
`npm run web` renders the same app in a browser, which is handy for quick layout
checks (see *Platform notes* for what does not work there).

```bash
npm test        # core pipeline tests
npm run typecheck
```

## How it reads your training

The headline metric is **hard sets per muscle per week**. Warm-up sets are excluded.
Each set counts 1.0 toward the exercise's primary muscles and 0.5 toward its
secondaries.

Volume load (Σ weight × reps) was deliberately rejected after measuring both
against a real export. It misclassifies light-but-frequent work: side delts read
ice-cold despite decent frequency because lateral raises are a few kilos, while a
rarely-trained muscle reads hot off one heavy machine exercise. Set count is what
answers "what am I neglecting".

**Four time windows:** 1 week, 1 month, this year, 1 year. Three are fixed
look-back intervals; "this year" is the odd one out, running from 1 January of the
anchor's year, so its length depends on when in the year you look.

**Windows are anchored to the most recent workout in the file, not to today.** An
export a few months old would otherwise render an empty map, which looks like a bug
rather than like stale data. The header names both ends of the window.

The per-week divisor never counts weeks that predate your first logged workout, so a
short export viewed at "1 year" does not read as though fifty weeks had been skipped.

**Two colour scales.** *Relative* divides by your busiest muscle, so the map uses the
full range and stays readable whatever your training frequency. *Absolute* divides by
a fixed 20 sets/week reference, so different windows and different imports are
directly comparable. Both scales show the same underlying sets/week figure.

A muscle with no logged sets renders in a neutral grey, never at the cold end of the
ramp — "not trained" and "least trained" must not look alike.

## Layout

```
src/core/     pure TypeScript — no React Native imports, runs under plain Node
  types.ts               domain types
  parseCsv.ts            CSV text -> SetRow[]
  exerciseMuscleMap.ts   exercise table + normalisation + keyword fallback
  aggregate.ts           sets + window -> sets/week per muscle
  colorScale.ts          value -> hex
  bodySlugs.ts           our muscle taxonomy -> the renderer's slugs
src/ui/       React Native components
fixtures/sample-export.csv             synthetic test fixture (see Privacy)
```

Everything worth trusting lives in `src/core` and is unit-tested without a simulator
in the loop. `npm test` runs 96 tests against the fixture, including a ground-truth
check on the full 8-week muscle ranking — the expected figures were derived
independently of the implementation, so the suite catches drift rather than
re-stating whatever the code happens to do.

## Privacy

The app is entirely client-side: a CSV you pick is parsed in memory and never
leaves the device. There is no backend, no analytics and no persistence.

**Real exports are never committed.** A StrengthLog export contains bodyweight and
a dated training history. `fixtures/*.csv` is gitignored apart from
`sample-export.csv`, which is synthetic — generated by `scripts/make-fixture.mjs`
and built to reproduce the parser's edge cases rather than anyone's training. The
published build contains no sample data at all; the only way in is to import your
own file.

## Export format notes

Three things about StrengthLog's CSV that break naive parsing, all handled in
`parseCsv.ts`:

1. **The header contains `calories` twice** — a set-level cardio figure at index 14
   and a daily wellness score at index 24. Any header-keyed parse silently drops one.
   The parser works from column indices and resolves duplicates deliberately.
2. **Workout names contain commas** and are quoted, so a real CSV parser is required.
3. **Exercise names use typographic punctuation** — `Captain’s Chair Knee Raises`
   carries U+2019, which Unicode normalisation alone does not fold.

Eight different set shapes appear in practice: weight+reps, bodyweight+reps,
bodyweight+time, bodyweight+extraWeight+reps, distance+time, weight+distance,
bodyweight+assistingWeight+reps, and bodyweight+height+reps.

## Installing it on a phone

Styrklog is built to live on an iPhone home screen as a web app — no Apple
developer account, no signing, no 7-day expiry, and updates ship by redeploying.

```bash
npm run build:web     # -> dist/
```

That runs Expo's web export and then decorates the output, because Expo emits a
bare index.html with no PWA metadata and no service worker (SDK 57 has `expo.web`
manifest config but does not generate a worker). `scripts/build-web.mjs` injects
the manifest link and the Apple tags that "Add to Home Screen" reads, and writes a
service worker precaching the exact hashed filenames that build produced.

Serve `dist/` from the **root** of an HTTPS host — Expo emits absolute asset paths
(`/_expo/...`), so a subdirectory deploy needs `experiments.baseUrl` set as well.
Then on the phone: open the URL in Safari, Share -> Add to Home Screen.

Offline launch is verified: with the server stopped, a URL that had never been
requested still rendered the app, which only the worker's navigation fallback can
do.

### What you give up

The app cannot appear in StrengthLog's share sheet. iOS has never implemented the
Web Share Target API, so no home-screen web app can register as a share target.
The import route is: export -> Save to Files -> open Styrklog -> Import. Putting
Styrklog in that share sheet would require a native build and Apple signing.

### The icon

`scripts/make-icon.mjs` composes `web/icon.svg` from the same body artwork the app
draws, so the icon is the app rather than a placeholder. Rasterising it to PNG used
a browser canvas, which is not reproducible headlessly — so the generated PNGs in
`public/icons/` are committed rather than built. Re-run the script and re-rasterise
only if the artwork changes.

## Exercise mapping

`exerciseMuscleMap.ts` maps exercise names to muscles. It covers the StrengthLog
exercises seen so far explicitly. Anything it has not seen falls through to ordered
keyword heuristics (`leg curl` is matched as hamstrings before `curl` is matched as
biceps, and so on); anything the heuristics miss is not counted at all.

Both cases are surfaced in the app's **Exercise coverage** sheet — inferred exercises
are labelled as guesses, unmapped ones as not counted. The map should never be
quietly confident about training it has not accounted for.

To add an exercise, add a row to the table. The test suite asserts that every
exercise in the fixture resolves via the explicit table, so the table cannot
silently rot into heuristics.

## Platform notes

The target is iOS, and the app has been run and verified on an iPhone simulator:
the muscle tap, the multi-muscle drill-down, and the full DocumentPicker import
from the Files app all work there.

`npm run web` also works and is handy for quick layout and data checks, with one
caveat: **tapping a muscle on the body does not work in the browser**.
react-native-svg's `onPress` rides on React Native's responder system, which
react-native-web does not wire onto SVG elements. Use the ranked list to reach the
same drill-down when previewing on web.

### Running on the simulator

Xcode must be selected (`sudo xcode-select -s /Applications/Xcode.app/Contents/Developer`)
and an iOS runtime installed (`xcodebuild -downloadPlatform iOS`, ~8.5 GB) — recent
Xcode versions ship without one. Then `npm start` and press `i`.

To test the import path on a simulator, get a CSV into its Files app first: serve the
sample over HTTP and download it through Safari in the simulator, which lands it in
Files › Downloads where the picker can reach it.

## Rendering

The bodies come from [`react-native-body-highlighter`](https://github.com/HichamELBSI/react-native-body-highlighter)
(MIT). Two things about it are worth knowing before editing `bodySlugs.ts`:

- **Its `defaultFill` prop is effectively dead.** Every path in its SVG assets ships
  with a baked-in `color: '#3f3f3f'`, and the merge only overrides that for slugs
  present in the `data` array. Any region you do not colour explicitly renders near
  black — which, on a map where dark means high volume, reads as the most-trained
  thing on screen. `DECORATIVE_SLUGS` exists to neutralise head, hands, feet and knees.
- **Its README advertises an `abductors` slug that does not exist** in the shipped
  assets. A compile-time guard in `BodyHeatMap.tsx` catches this class of mistake by
  asserting our mirrored slug union is assignable to the library's.

Our internal taxonomy is finer than the library's slug list. Front and back render as
two separate `<Body>` instances with their own data arrays, which is what lets the
single `deltoids` slug show front delts on the front view and rear delts on the back.
Where several muscles share one slug (back `upper-back` covers lats and rhomboids) the
region takes the **max** of its constituents, never the sum; the drill-down splits it
back apart.
